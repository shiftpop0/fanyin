# RTX 5090 真实普通话长音频单双进程性能评估计划

更新时间：2026-09-02  
状态：真实音频数据和接口口径均已获用户确认；单进程基线执行中，随后进行长音频超时阶梯复测、8885 可靠性子集和双进程测试。

## 1. 评估目标

本轮只评估当前单卡 RTX 5090 在约 20,000 分钟/日音频转译业务中的时间、吞吐、显存和稳定性，不把模型识别准确率或说话人区分准确率作为主要目标。

重点比较：

1. 单进程与双进程的吞吐差异；双进程各配置约 16GB 显存预算。
2. `diarize=0` 与 `diarize=1` 的端到端耗时、实时率、显存、GPU 利用率和失败率差异。
3. `diarize=1` 强制经过说话人分离模块后产生的性能损耗。
4. `diarize=0/1` 各占约 50% 的混合工作负载表现。
5. 根据稳态有效吞吐，估算每日 20,000 分钟总音频量所需的 RTX 5090 数量。

`diarize=1` 不要求素材真的包含多名说话人，也不以 DER 或真实分人准确率作为主要验收指标。

## 5. 测试矩阵

### 5.1 单进程

1. 预热，不把模型加载和首次编译时间混入稳态吞吐。
2. 主体集全部按 `diarize=0` 推理。
3. 主体集全部按 `diarize=1` 推理。
4. 主体集按累计分钟严格 50/50 混合：
   - `diarize=0`：33 份、543 分钟；
   - `diarize=1`：33 份、543 分钟。
5. 六安采访分别以 `diarize=0/1` 做补充测试。

### 5.2 双进程

1. 经用户授权，测试期间停止但不删除当前单进程服务。
2. 启动两个隔离实例，每个实例目标显存预算约 16GB。
3. 重复单进程的三组主体测试和采访补充测试。
4. 记录是否出现 OOM、容器重启、请求失败或显存无法满足完整服务的问题。
5. 测试结束后恢复原单进程服务，并重新验证 6006/8885 健康状态。

## 6. 指标

每个文件至少记录：

- 音频分钟数；
- 队列等待时间；
- 端到端墙钟时间；
- 实时率 RTF = 处理秒数 / 音频秒数；
- 吞吐倍速 = 音频秒数 / 处理秒数；
- 每小时可处理音频分钟数；
- GPU 利用率、显存峰值；
- CPU、内存；
- HTTP 状态、服务错误、超时、重试；
- 输出是否为空、是否包含完整尾段等基本完整性检查。

统计平均值、p50、p90、最慢值，并分别报告短音频、中等音频和 60～120 分钟长音频。

准确率不作为主要产能约束；仅做输出非空、长度合理、无明显截断或乱码等质量卫生检查。六安采访可额外做一次参考文本抽查，但不据此评判说话人分离正确率。

## 7. 20,000 分钟/日产能换算

以稳态有效吞吐计算：

`单卡日产能（分钟） = 24 × 60 × 吞吐倍速 × 可用率 × 安全系数`

建议至少报告：

- 理论值：不扣可用率；
- 计划值：可用率 90%；
- 保守值：可用率 80%，并预留峰值和失败重试空间。

`所需卡数 = ceil(20,000 / 单卡日产能)`

单进程和双进程分别计算；若双进程更快但频繁 OOM、失败或无法运行完整链路，则不把它计为有效生产能力。

## 8. 接口口径门禁

当前实测发现 8885 平台接口的 ForcedAligner 在参考音频上出现过 `E016 / HTTP 500`，但原生 6006 ASR 成功。

建议口径：

- 6006 原生接口：完成全部性能主测试；
- 8885 平台接口：完成可靠性子集，单独统计平台强制对齐阶段的额外耗时和失败。

如果要求全部走 8885，应先修复或接受 ForcedAligner 故障可能污染 RTX 5090 性能结论的风险。该口径需在正式推理前由用户确认。

## 10. 长音频说话人分离超时阶梯复测

对 60 秒基线下发生 `Diarization timeout` 并降级为整段 ASR 的全部 30～120 分钟长音频，执行以下门禁：

1. 第一轮将服务端 `diarization_timeout` 提高到 180 秒，重测全部基线降级样本。
2. 仅对 180 秒仍未完成说话人分离的样本，将阈值提高到 600 秒并再次重测。
3. 只有在 600 秒最终阈值仍未返回有效说话人分离结果时，报告才允许把该样本记为“可降级”。
4. 每轮保存实际生效的配置、服务健康状态、逐文件耗时、响应、GPU 秒级采样和成功/降级状态。
5. 超时阶梯完成后恢复原始 60 秒配置并验证 6006 与 8885 健康状态。

需要特别审计当前实现中 `ThreadPoolExecutor` 在超时异常退出时等待工作线程结束的行为：服务端标记为 60 秒超时，不一定意味着请求在 60 秒即刻结束。报告将区分“配置阈值”和“实际端到端耗时”。
