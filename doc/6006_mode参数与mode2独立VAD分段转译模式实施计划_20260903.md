# 6006 `mode` 参数与 `mode=2` 独立 VAD 分段转译模式实施计划

计划日期：2026-09-03

计划状态：代码实施与 RTX 5090 真实模型验收完成，尚未部署生产

当前范围：6006 FastAPI 服务

问题参考：[`/asr_raw` 短音频静默截断技术问题单](../wxz/benchmark_5090/短音频_asr_raw_静默截断技术问题单_20260903.md)

## 1. 本轮最终决策

本轮不再重新定义或修复 `diarize=0`/`diarization=false`，而是在 6006 原生服务的
`POST /asr` 上增加可扩展整数参数 `mode`。

当前只实现两种 `mode`：

| 参数 | 模式名称 | 分段来源 | 说话人区分 | 时间戳 | 当前状态 |
| --- | --- | --- | --- | --- | --- |
| `mode=1` | 说话人分离转译 | TargetDiarization | 有 | 有 | 复用当前 `diarization=true` |
| `mode=2` | 独立 VAD 分段转译 | FSMN VAD | 无 | 有 | 本轮新增 |

`mode` 是后续可继续扩展的模式选择器，不应在实现中写成仅支持布尔分支的临时逻辑。
请求解析、日志和路由分发均应按模式注册或显式映射，后续增加 `mode=3` 等模式时不必
再次重构接口。

本轮明确不包含：

- `diarization=false` 或业务口径中的 `diarize=0` 完整性修复；
- `/asr_raw` 静默截断修复；
- `mode=0` 实现；
- 8885 `/v1/audiototext` 的 `mode` 参数；
- 8885 对 mode 结果的继承、转换或二次扩展；
- 模型训练、模型替换、权重修改或模型参数调优。

上述项目统一列入未来工作，不能在本轮实现中顺带改变。

## 2. 参数合同

### 2.1 6006 当前真实参数名

6006 `POST /asr` 源码中的现有查询参数名是：

```text
diarization
```

8885 `/v1/audiototext` 使用的参数名才是：

```text
diarize
```

因此，本轮 6006 的互斥规则在代码中必须针对 `mode` 与 `diarization`。需求讨论中提到
的“mode 与 diarize 不得同时传入”，在 6006 实际实现里等价于：

```text
mode 与 diarization 不得同时出现在同一个请求中
```

本轮不为 6006 新增 `diarize` 别名，避免把两个端口的参数合同混在一起。

### 2.2 参数互斥

只要请求 URL 同时出现 `mode` 和 `diarization`，无论二者是否等价，都直接返回参数
错误，不做优先级覆盖，也不静默忽略其中一个参数。例如：

```text
/asr?mode=1&diarization=true   → 参数错误
/asr?mode=1&diarization=false  → 参数错误
/asr?mode=2&diarization=false  → 参数错误
```

建议使用 HTTP 400，错误信息明确指出二者互斥：

```json
{
  "detail": "mode and diarization cannot be used together"
}
```

实现时不能仅依赖 `diarization: bool = False` 的解析结果判断，因为这样无法区分“客户端
没有传参数”和“客户端明确传了 `diarization=false`”。应将其改为可检测缺省状态的
可选参数，或直接检查原始 query parameter 是否存在。

### 2.3 请求分发表

| 请求 | 本轮行为 |
| --- | --- |
| `/asr?mode=1` | 执行当前说话人分离 + 分段批量 ASR |
| `/asr?mode=2` | 执行独立 VAD + 分段批量 ASR |
| `/asr?diarization=true` | 保持当前行为，兼容旧客户端 |
| `/asr?diarization=false` | 保持当前旧 d0 行为，本轮不修复 |
| `/asr` | 保持当前默认行为，本轮不修复 |
| `/asr?mode=0` | 当前未实现，返回不支持的 mode 参数错误 |
| `/asr?mode=3` 或其它未知值 | 返回不支持的 mode 参数错误 |
| `/asr?mode=1&diarization=true` | 返回参数冲突错误，不因含义相同而放行 |

当前建议 `mode` 使用严格整数解析，不接受 `1.0`、`true`、`vad` 等隐式变体。错误响应
应区分“格式错误”和“当前不支持的模式值”，便于后续扩展和调用方排查。

### 2.4 兼容原则

- 旧客户端继续使用 `diarization=true/false`，本轮行为不变；
- 新客户端使用 `mode`；
- `mode=1` 是旧 `diarization=true` 的新参数入口，但不是覆盖旧参数；
- 两套参数只允许二选一，不建立优先级；
- 本轮不宣布弃用 `diarization`；
- mode 的未知值必须失败，不能默认落入 mode 1、mode 2 或旧 d0。

## 3. 模式语义

### 3.1 `mode=1`：当前说话人分离模式

`mode=1` 完整复用当前 `POST /asr?diarization=true`：

```text
音频输入
  → TargetDiarization
  → 说话人片段
  → 按片段裁剪
  → ASR 批量推理
  → 按时间顺序聚合
  → speaker_segments + overall_text
```

本轮只增加入口映射，不改变以下行为：

- TargetDiarization 模型装载和调用；
- speaker 标识与 `speaker_count`；
- 片段开始/结束时间；
- 批量 ASR 与逐段重试；
- `overall_text` 聚合顺序；
- 当前 6006 原生 JSON 字段；
- 当前超时和降级策略。

`mode=1` 的首要验收要求是与 `diarization=true` 等价，不得因为提取公共代码而产生
文本、片段、speaker、时间或响应结构回归。

### 3.2 `mode=2`：独立 VAD 分段转译模式

`mode=2` 的目标是：保留 mode 1 的分段、时间戳、批量 ASR、顺序聚合和调试能力，
只移除说话人识别与说话人区分。

目标链路：

```text
音频输入
  → 完整解码并标准化为 mono float32 16 kHz
  → 独立 FSMN VAD
  → VAD 语音时间片段
  → 片段合法性校验与按时间排序
  → 按片段裁剪
  → 当前 ASR 模型批量推理
  → 必要时执行当前逐段重试
  → 按原索引和时间顺序聚合
  → segments + overall_text
```

mode 2 不调用：

- `DiarizationWrapper.diarize()`；
- `UnifiedService.diarization_only()`；
- TargetDiarization 对象内部的 VAD；
- CAM++；
- Pyannote；
- 说话人 embedding、聚类或 speaker 标签修正；
- ForcedAligner。

### 3.3 mode 1 与 mode 2 的差异边界

| 能力 | `mode=1` | `mode=2` |
| --- | --- | --- |
| 完整音频解码 | 有 | 有 |
| 分段 | 有 | 有 |
| 片段时间戳 | 有 | 有 |
| 分段裁剪 | 有 | 有 |
| ASR 批量推理 | 有 | 有 |
| 批量失败后的逐段重试 | 有 | 有 |
| 按原时间顺序聚合 | 有 | 有 |
| `overall_text` | 有 | 有 |
| 说话人模型 | 有 | 无 |
| speaker 区分 | 有 | 无 |

这一定义确保 mode 2 不是“先跑说话人模型，再把 speaker 全部改成同一个值”，也不是
“整段音频直接 ASR”。它必须使用独立 VAD 作为片段生产器。

## 4. `mode=2` 响应合同

mode 2 是 6006 新功能，没有旧客户端兼容负担。建议使用与 mode 1 平行、但不伪装成
说话人结果的结构：

```json
{
  "input_file": "sample.wav",
  "mode": 2,
  "segmentation_status": "ok",
  "overall_text": "按时间顺序聚合的完整转译文本",
  "segments": [
    {
      "start": 0.22,
      "end": 3.53,
      "type": "single",
      "text": "第一个语音片段的转译文本",
      "asr_debug": {
        "segment_index": 0,
        "attempts": 1,
        "empty_segment": false,
        "request_id": "sample.wav-..."
      }
    }
  ],
  "segment_count": 12,
  "completed_segment_count": 12,
  "detected_languages": ["Chinese"],
  "input_duration_seconds": 120.0,
  "vad_speech_duration_seconds": 109.4,
  "timing_debug": {},
  "segment_workers_effective": 32,
  "request_id": "sample.wav-..."
}
```

响应设计原则：

- 使用 `segments`，不使用 `speaker_segments`；
- 片段不包含 `speaker` 字段；
- 不返回 `speaker_count`；
- `overall_text` 必须等于所有非空 segment text 按时间顺序直接拼接；
- `start/end` 继续使用与 mode 1 相同的秒单位；
- 每一个 VAD 片段都必须有对应的处理状态；
- 模式标识固定返回 `mode: 2`，便于客户端和日志识别。

如果为了减少第一版响应改动而必须复用 mode 1 外层结构，也只能将 speaker 固定为单一值
作为兼容投影；通用内核仍应使用无 speaker 的 `segments`，不能让说话人字段成为 mode 2
内部处理的必要条件。

## 5. “真正跳过说话人模型”的验收定义

mode 2 必须拥有独立调用链。验收要求：

1. mode 2 不调用任何 TargetDiarization 实例方法；
2. 独立 VAD 使用 FunASR `AutoModel` 直接加载仓库现有 FSMN VAD；
3. `service.diarization=None` 时 mode 2 仍可运行；
4. diarization 初始化失败只影响 mode 1，不影响 mode 2；
5. 单元测试放置“一旦被调用就抛错”的假说话人对象，mode 2 必须成功；
6. 请求期日志只能出现 `[VAD]`、`[SEG-ASR]` 等阶段，不出现请求期 `[DIAR]` 推理；
7. 代码审查确认 mode 2 未通过 TargetDiarization 内部的 ASRProcessor/VAD 间接执行。

当前同一个 6006 进程仍需支持 mode 1，因此说话人模型可以在服务启动时继续装载和驻留。
“跳过”在本计划中的准确含义是 mode 2 请求不执行、不依赖说话人推理。若以后要求某个
部署实例完全不装载说话人模型、释放其显存或内存，需要另立“按模式延迟加载/独立部署”
计划，不能在本轮擅自改变 mode 1 的启动行为。

## 6. 可行性与现有基础

### 6.1 独立 VAD 模型已经存在

本地模型路径：

```text
tailect/model/iic/speech_fsmn_vad_zh-cn-16k-common-pytorch/
```

该模型任务为 `voice-activity-detection`，可通过 FunASR `AutoModel` 独立加载。本地
README 已给出 `AutoModel(model="fsmn-vad")` 和 `generate(input=wav_file)` 的调用方式。
当前配置包含：

```text
max_end_silence_time: 800 ms
max_single_segment_time: 60000 ms
```

因此不需要新增、下载或训练模型。

### 6.2 mode 1 已经验证下游分段 ASR

当前 `UnifiedService.transcribe_diarized_segments()` 已实现：

- 按片段裁剪音频；
- `transcribe_batch_detailed()` 批量推理；
- 批量异常或超时时逐段重试；
- 按输入索引重新组装；
- 聚合 `detected_languages`；
- 拼接 `overall_text`；
- 输出调试字段。

mode 2 可以复用这部分能力。所需的主要工程工作是将“片段生产”和“片段 ASR”解耦，
而不是重新实现 ASR 或修改模型。

### 6.3 可行性结论

该方案开发可行性高。关键能力已经存在，主要风险集中在工程边界而非模型效果：

- 独立 VAD 与说话人模块是否真正解耦；
- 8 kHz 等非 16 kHz WAV 是否正确标准化；
- VAD 毫秒时间是否正确转换；
- 批量结果是否与输入片段一一对应；
- mode 1 公共代码抽取后是否保持原行为；
- 异常时是否再次静默返回局部文本。

这些风险都可以通过固定问题样本、隔离测试和接口合同测试验证。

## 7. 目标内部架构

```text
POST /asr
  → 参数存在性与互斥校验
  → ModeDispatcher
       ├─ mode=1 → DiarizationSegmentProvider
       └─ mode=2 → VadSegmentProvider
  → CommonSegmentAsrEngine
       ├─ clip_audio
       ├─ transcribe_batch_detailed
       ├─ sequential retry
       ├─ result cardinality/order validation
       └─ overall aggregation
  → Mode-specific response projector
```

建议用明确的模式常量或枚举代替散落的数字比较，例如：

```python
MODE_SPEAKER_DIARIZATION = 1
MODE_VAD_SEGMENT = 2
```

但对外仍使用整数。模式解析和分发集中在一处，避免在多个函数中反复编写
`if mode == 1 / elif mode == 2`。

## 8. 音频与 VAD 分段规则

### 8.1 单次标准化

mode 2 必须完整读取输入，并在内存中形成：

```text
mono + float32 + 16000 Hz
```

VAD 和后续片段裁剪必须共享同一份音频缓冲和采样率，避免二次解码或不同重采样实现导致
时间轴错位。

当前 6006 `ensure_wav_audio()` 对 WAV 后缀直接返回原文件，问题材料又是 8 kHz WAV，
所以不能把“已经是 WAV”视作“已经是 16 kHz 单声道”。mode 2 的内存标准化必须独立于
文件容器转换逻辑。

### 8.2 VAD 输出标准化

内部标准结构：

```python
[
    {"start": 0.22, "end": 3.53, "type": "single"},
    ...
]
```

需要完成：

1. 毫秒到秒的单位转换；
2. 边界限制在 `[0, input_duration]`；
3. 非数值、负值及 `end <= start` 校验；
4. 按 `start/end` 稳定排序；
5. 重叠、倒序和重复片段处理；
6. 超长单片段的确定性二次切分；
7. 片段数量、语音总时长与首尾时间日志。

第一版沿用当前本地 VAD 模型配置，不在没有实测依据时调整
`max_end_silence_time`、阈值或模型文件。参数调优属于后续优化。

## 9. 失败与完整性策略

mode 2 不得使用以下降级：

- VAD 不可用时回到整段 `/asr_raw`；
- VAD 异常时将整段音频伪造成单片段；
- VAD 失败后改用说话人模型分段；
- 批量结果少于输入片段时返回局部 overall；
- 逐段重试失败后用空文本掩盖异常；
- 时间轴异常时继续裁剪或返回成功。

规定行为：

- VAD 合法返回零片段：视为 `no_speech`，返回空文本和空 segments；
- VAD 初始化或推理异常：返回明确失败；
- ASR 批量异常：允许使用 mode 1 已有的逐段重试；
- 重试后仍发生执行异常：整次请求失败；
- 某片段正常完成但文本为空：记录 `empty_segment=true`，继续其它片段；
- `completed_segment_count` 必须与 `segment_count` 一致；
- `overall_text` 必须由全部已完成片段按顺序生成，不接受提前返回。

## 11. 实施阶段

3. 建立可扩展模式分发器；

### 阶段 C：独立 VAD

1. 实现独立加载器和包装器；
2. 实现音频标准化；
3. 实现 VAD 结果解析与校验；
4. 增加健康状态和故障隔离；

### 阶段 D：公共分段 ASR 内核

1. 从当前 d1 中抽取裁剪、批量 ASR、重试、排序和聚合；

### 阶段 E：本地和目标环境验收

4. 记录时长、片段数、文本、耗时、显存和错误；
5. 验收完成后再更新生产状态，不提前写成已上线。

## 12. 验收标准

### 12.1 参数与接口

1. `/asr?mode=1` 正常执行当前 d1；
2. `/asr?mode=2` 正常执行新 VAD 模式；
3. mode 与 diarization 同时出现必定 HTTP 400；
4. 未支持的 mode 不会进入任何推理模型；
5. `/asr_raw`、旧 true/false 参数及 8885 行为未被意外修改。

### 12.2 mode 2 功能

1. 独立 VAD 返回有序时间片段；
2. 所有片段均经过当前 ASR 批量或重试流程；
3. `completed_segment_count == segment_count`；
4. overall 等于各片段文本顺序拼接；
5. 返回片段有时间戳但没有 speaker 区分；
6. mode 2 不调用说话人模型和 ForcedAligner；
7. VAD/ASR 执行失败不会以局部文本返回成功。

### 12.3 问题样本验证

问题单四份材料虽然来自旧 `/asr_raw` 故障，但可作为 mode 2 完整性基准：

- 120、180、240、300 秒输入时长均被完整读取；
- mode 2 处理全部 VAD 语音片段；
- mode 2 不应出现旧 d0 仅 8～22 个字符的静默截断；
- mode 2 overall 与 mode 1 overall 的明显内容差异必须人工复核；
- 本轮结果不能写成“`/asr_raw` 已修复”，因为该入口不在范围内。

### 12.4 模型不变

实施前后以下模型文件 SHA-256 必须一致：

- Tailect V4.1 ASR；
- FSMN VAD；
- CAM++/Pyannote 等说话人模型；
- Qwen3 ForcedAligner；
- 标点模型。

任何模型权重、配置、tokenizer 或生成参数的变化均超出本计划，必须停止并另行确认。

### 12.5 性能边界

- 保持单模型进程；
- 保持现有 FIFO 单并发约束；
- 不擅自改变 `vllm_gpu_memory_utilization=0.7`；
- 分别记录 VAD、裁剪、批量 ASR、逐段重试和总耗时；
- 在目标 GPU 实测前不承诺具体性能增益。

## 13. 风险与控制

| 风险 | 后果 | 控制 |
| --- | --- | --- |
| mode 与旧参数优先级不清 | 同一请求行为不确定 | 严格互斥，同时出现即 HTTP 400 |
| 布尔默认值掩盖参数存在性 | 无法识别显式 false | 检查原始 query 或使用可选参数 |
| mode 2 借用 TargetDiarization 内部 VAD | 实际未跳过说话人组件 | 独立加载器、隔离测试、调用图审查 |
| 8 kHz WAV 未标准化 | 时间轴或 VAD 输入错误 | 内存统一 mono float32 16 kHz |
| VAD 切段过碎/尾音截断 | 文本质量下降 | 第一版保留模型默认值，实测后再调优 |
| 批量结果索引错位 | 文本顺序错误 | 校验数量并按稳定索引组装 |
| 异常片段被空文本掩盖 | 局部文本假成功 | 执行异常重试耗尽后整请求失败 |
| 抽取公共内核改变 mode 1 | 稳定能力退化 | 先冻结 d1 基线，做结构和内容回归 |
| 顺手修改 d0 或 8885 | 范围失控 | 自动测试断言相关入口保持不变 |

## 14. 未来工作，不属于本轮

### 14.1 `mode=0` 与旧 d0 完整性修复

未来可定义：

```text
mode=0 = overall-only
```

其对外结果只表达完整转译文本，不暴露语音片段、说话人或细粒度时间戳。内部如何获得
完整 overall，应以 mode 1 已验证的完整性为基线；可以复用分段 ASR 内核，但对外只做
全文投影。该设计需要与 `/asr_raw`、`diarization=false` 的兼容和迁移一起制定，不能在
本轮 mode 2 开发中隐式完成。

### 14.2 8885 对 mode 的继承与扩展

8885 是建立在 6006 能力上的扩展接口，未来可以照搬 mode，也可以在 mode 基础上形成
平台自己的响应投影。本轮不修改 8885。

如果未来 8885 支持 `mode=0`，平台现有字幕行合同仍可保持：将完整转译内容作为一条行，
时间范围使用整段音频：

```json
{
  "lid": "1",
  "text": "完整转译内容",
  "begin": 0,
  "end": 120000
}
```

即界面语义为：

```text
00:00:00 ～ 音频结尾：完整转译内容
```

这不会破坏 `data` 行仍包含 `lid/text/begin/end` 的平台合同，但属于 8885 的适配策略，
不等于 6006 mode 0 必须返回细粒度时间戳。

### 14.3 后续 mode 扩展

未来 mode 值必须登记名称、分段来源、模型依赖、响应合同和错误策略。新增 mode 不得复用
未知值回退逻辑，也不得改变已发布 mode 1、mode 2 的含义。

## 15. 回滚原则

mode 2 是新增入口，回滚时可以按完整发布版本撤回该入口，但不能删除历史文件或测试
材料。mode 1 和旧 `diarization` 路径应始终保持可验证基线。

禁止在 mode 2 内设置静默回退到旧 `/asr_raw` 或说话人分离流程的隐藏开关。失败时应
明确失败，便于定位。

## 16. 完成定义

只有同时满足以下条件，才能把计划状态改为“完成”：

1. 6006 `/asr` 已实现严格互斥、可扩展的 mode 分发；
2. mode 1 与当前 `diarization=true` 等价；
3. mode 2 使用独立 VAD，返回有时间片的无说话人结果；
4. mode 2 不执行或依赖任何说话人推理；
5. 问题样本在 mode 2 下不出现静默截断；
6. mode 1 回归通过；
7. `/asr_raw`、旧 d0 和 8885 未被本轮改变；
8. 模型文件哈希保持不变；
9. 目标 Ubuntu/GPU 环境完成验证并保留结果；
10. 接口说明、测试记录和计划状态同步更新。

以上条件已于 2026-09-03 在 RTX 5090 开发测试服务器完成验证，详见第 17 节及
[`RTX5090 mode 2 真实模型验收报告`](../wxz/benchmark_5090/mode2_validation_20260903/RTX5090_mode2真实模型验收报告_20260903.md)。
