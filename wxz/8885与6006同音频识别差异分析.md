# 8885 与 6006 同音频识别差异分析

分析日期：2026-08-30
分析范围：当前仓库代码，以及 `wxz/日志/test1/` 下的 `0051409.wav`、`test_result.json`、`test_result_6006.json`。

> 文档状态：本文记录 R9 实施前的 R8/原扩展链路及问题证据。R9 已按本文 P0 建议
> 改为共享分段批量 ASR 核心；实施详情和生产验收方法见
> [R9：8885 复用 6006 原生转译能力实施与验收](./docs/R9_8885复用6006原生转译能力实施与验收.md)。

## 一、结论摘要

**8885 效果差的主因不是端口、Nginx、GPU 或模型文件不同，而是 8885 扩展接口与 6006 对照请求走了不同的识别流水线。**

- 8885 的 `/v1/audiototext?diarize=1` 当前执行顺序是：**整段音频一次 ASR → 全文强制对齐 → 另做说话人分离，只给字幕贴 `lid`**。
- 6006 结果的 JSON 结构可以确定它来自 `/asr?diarization=true`，执行顺序是：**先说话人分离成 18 个短片段 → 每个短片段分别 ASR → 按时间顺序拼接**。
- 两条链路使用的是同一个 6006 模型进程和同一个 `Tailect_V4.1` ASR 实例；8885 只是反向代理入口。
- 本样本是 63.29 秒、8 kHz、单声道、G.711 A-law 电话录音。对这种方言、电话窄带、双人轮流通话，短片段 ASR 明显比整段一次生成稳定。
- 8885 的整段 ASR 已经漏掉后半段内容并产生重复；ForcedAligner 只能把已有的错误文字硬贴到时间轴，不能补回漏识别内容，反而把错误暴露为异常长时间段。

因此，**当前扩展 API 的 `diarize=1` 与 6006 的 `diarization=true` 名字相似、实际语义不同**。这是本次差异的核心。

## 三、两条真实调用链

### 3.1 8885 扩展 API

部署配置证明 8885 没有运行第二套模型：

```text
客户端 :8885 /v1/audiototext
        ↓ Nginx proxy_pass
同一 FastAPI :6006 /v1/audiototext
        ↓
transcribe_platform_audio()
        ↓
service.asr_raw(完整 63.29 秒音频)
        ↓
service.forced_align(完整音频, ASR 全文)
        ↓
diarize=1 时另外调用 service.diarization_only()
        ↓
按时间重叠给字幕行分配 lid
```

关键证据：

- `wxz/deploy/nginx_platform_8885.conf:17-19`：8885 的 `/v1/audiototext` 原样代理到 `127.0.0.1:6006`。
- `wxz/deploy/run_v4_1_single_4090.sh:2`：明确写明一个 6006 模型进程和一个 8885 平台代理。
- `tailect/core/v1_adapter.py:62`：首先调用 `service.asr_raw(audio_path)`，输入是完整文件。
- `tailect/core/v1_adapter.py:69`：再对 ASR 全文做 ForcedAligner。
- `tailect/core/v1_adapter.py:72-78`：`diarize` 只在 ASR 和对齐之后执行。
- `tailect/core/v1_contract.py:207`：说话人结果仅用于给已经形成的字幕行选一个最大重叠 `lid`。

所以 8885 的“区分说话人”目前只是**结果标注功能**，不会用说话人边界改善 ASR。

### 3.2 6006 对照结果

`test_result_6006.json` 含 `overall_text`、`speaker_segments`、`diarization_status=ok`、`segment_workers_effective=32`，与 `UnifiedService.diarization_then_asr()` 返回结构完全一致，可确定来自 6006 的 `/asr?diarization=true` 链路：

```text

        ↓

        ↓
得到 18 个 1.00–10.01 秒说话人片段
        ↓

        ↓

```

关键证据：

- `tailect/core/api_server.py:395-401`：`diarization=true` 时调用 `diarization_then_asr()`。
- `tailect/core/inference_engine.py:1005-1016`：先运行说话人分离并生成片段。
- `tailect/core/inference_engine.py:1074-1089`：裁剪所有片段后，以短音频列表进行批量 ASR。
- `tailect/core/inference_engine.py:1147-1189`：每个片段保留原始说话人时间，并拼接 `overall_text`。

## 四、原因分级

### 4.1 已证实的首要原因：识别前是否切段

6006 把 63 秒双人通话变成 18 个短片段后识别；8885 把整段 63 秒一次送给模型。

短片段具有以下优势：

- 每次只包含一个较连续的说话人和较短上下文；
- 静音、换人、电话噪声不会在一次长生成中持续累积影响；
- 生成更短，不容易发生漏尾、重复短语或上下文漂移；
- 方言词在邻近语音内完成判断，不需要模型同时维持一分钟的对话状态。

本样本的现象正符合长段生成失败：8885 重复了“加油站对面”“电瓶偷走了”“水箱弄漏了”，随后漏掉姓名、案件确认、通知派出所和结束语；6006 虽仍有错词，但覆盖了完整通话。

### 4.2 已证实的次要原因：两条链路的音频预处理并不完全相同

当前 `ensure_standard_wav()` 名称看似会“标准化 WAV”，但代码只检查 RIFF/WAVE 文件头。只要输入已经是 WAV 容器，它就直接返回，不会把本样本的 8 kHz A-law 转成 16 kHz PCM16：

- `tailect/core/audio_input.py:229-232`：WAV 文件头有效就直接返回。
- `tailect/core/audio_input.py:237-247`：只有非 WAV 内容才调用 ffmpeg 转 16 kHz PCM16。

8885 的 `asr_raw()` 因而把原始 8 kHz A-law WAV 路径直接交给 Qwen ASR 的内部加载器。

6006 分段链路则先把音频解码为 `float32` 数组，再裁剪每段；`ASRWrapper._prepare_audio_input()` 发现采样率不是 16 kHz 时会显式重采样，并写成临时 WAV 后再交给模型：

- `tailect/core/inference_engine.py:574-580`：读取/解码为浮点数组。
- `tailect/core/inference_engine.py:1074-1078`：按说话人时间裁剪。
- `tailect/core/inference_engine.py:260-275`：非目标采样率时显式重采样到 16 kHz 并重新写 WAV。

Qwen 自己也可能对文件路径做解码和重采样，因此不能仅凭静态代码断言格式转换贡献了多少准确率差异；但可以确定：**两条路径进入模型前的处理方式不完全一致**。应在修复时统一，排除变量。

### 4.3 ForcedAligner 不是纠错模型，只会放大上游坏结果

8885 先得到缺失、重复的全文，再把这份全文交给 `Qwen3-ForcedAligner-0.6B`。ForcedAligner 的职责是“已有文字对应哪段音频”，不是重新听写，也不会发现和补回没出现在 ASR 文本中的姓名、通知语等内容。

所以 8885 返回了整数时间戳并不代表识别链路正确。17.509 秒的“什么电瓶”已经说明对齐可信度失效。

### 4.4 不是主要原因的因素

- **不是 8885 Nginx 改坏音频**：Nginx 只做 HTTP 反向代理，没有转码和正文修改配置。
- **不是加载了第二个较差模型**：启动脚本只有一个模型容器，8885 和 6006 共用它。
- **不是响应字幕行聚合导致漏字**：漏字在 `asr_raw` 已发生。
- **不是 `lid` 映射导致漏字**：`lid` 是 ASR 和强制对齐完成后才追加的标签。
- **响应中的 `language: "tiantai"` 不是本次差异的根因**：这是模型报告的方言标签被 v1 原样小写输出；请求中的同名兼容参数现已完全忽略。

## 五、为什么开发阶段没有提前发现

当前实现与项目扩展计划是一致的：计划中明确选择“当前 ASR 全文 → ForcedAligner → 说话人最大重叠分配 `lid`”。也就是说，这不是 Nginx 偶发故障，而是扩展适配层最初设计没有复用 6006 已经验证更好的“先分段再 ASR”路径。

现有单元测试也只验证了结构和调用顺序：

- `tailect/tests/test_v1_platform.py:67-90` 使用 FakeService，明确断言调用顺序是 `asr → align → diarization`；
- 测试验证了字段、时间戳、说话人映射和安全边界，但没有用真实电话方言音频比较 8885 与 6006 的文字一致性；
- `wxz/docs/Tailect_V4.1离线接口与部署.md` 已注明开发机实施过程中没有启动真实模型，准确率需要在离线生产环境验收。

所以扩展接口通过“合同正确性”测试，但没有通过“与原 6006 识别质量等价”的真实样本回归测试。

## 六、建议修复优先级

本次任务只做分析，没有修改推理代码。建议后续按以下顺序实施。

### P0：让 8885 的 `diarize=1` 复用“先分段再 ASR”

目标语义应改为：

```text
diarization_only → 按说话人片段裁剪 → transcribe_batch → 逐段生成平台字幕行
```

不要再先做一次完整音频 `asr_raw`，然后仅用 diarization 贴标签。平台行的 `lid`、`begin`、`end` 应直接继承说话人片段；如果一个片段需要按标点再拆行，可在该短片段内部做 ForcedAligner，而不是对整段错误全文做一次全局对齐。

这项修改最接近 6006 已出现的好结果，预期收益最大。

### P0：明确 `diarize=0` 的长音频策略

即使用户不需要说话人标签，也不应默认把较长电话录音永久绑定为整段一次生成。建议用 VAD/低能量点切成约 10–30 秒片段后 ASR，再按全局偏移合并；不要为了切段而伪造说话人。

当前 63 秒低于 `pure_asr_max_chunk_seconds=300`，因此不会触发 Qwen 的长音频自动切分；这正是短于 300 秒但仍可能在质量上需要切段的空档。

### P1：统一所有输入的模型前音频格式

无论文件扩展名是否为 `.wav`，按音频流属性检查并统一为：

```text
16 kHz、单声道、PCM signed 16-bit little-endian WAV
```

当前“WAV 文件头有效就跳过转换”只能保证容器格式，不能保证采样率和编码。统一格式后再做 A/B 测试，可以把解码/重采样差异从模型质量问题中剥离。

### P1：增加真实质量回归，而不只测 JSON 合同

至少将本次 `0051409.wav` 作为现场离线验收样本，固定检查：

- 8885 `diarize=1` 与 6006 `diarization=true` 使用相同识别策略；
- 输出覆盖到 63 秒结尾，不能在“你叫什么名字”处终止；
- 包含“我姓叶/叶海华”“通知派出所”“我人在那等”等尾部关键内容；
- 不再出现一个普通短句占 8–17 秒的异常时间戳；
- 两个说话人交替关系基本一致。

最好再制作人工逐字稿，计算 CER（字错误率）。字符数多只能证明“更完整”，不能单独证明每个字更准确。

### P2：增加可观测字段和日志

建议内部日志记录但不必破坏现有响应合同：

- `pipeline=whole_asr_align` 或 `pipeline=diarize_segment_asr`；
- 输入 codec、采样率、声道、时长，以及实际送入模型的格式；
- ASR 原文长度、最后有效说话时间、切段数量；
- ForcedAligner 中异常长 token/字幕段告警；
- 模型目录、后端（vLLM/Transformers）和代码版本。

这样以后看到“两个端口结果不同”时，可以直接证明请求究竟走了哪条链路。

## 七、推荐复测矩阵

修复前后均使用同一个 `0051409.wav`、同一模型进程、同一时间连续执行：

| 编号 | 接口 | 用途 |
| --- | --- | --- |
| A | `6006/asr?diarization=true` | 当前分段 ASR 参考 |
| B | `8885/v1/audiototext?...&diarize=1` | 目标修复链路 |
| C | `6006/asr_raw` | 单独确认整段一次 ASR 的原始输出 |
| D | `8885/v1/audiototext?...&diarize=0` | 验证无说话人模式的切段策略 |

验收不能只看总字符数，至少同时看：人工逐字稿 CER、尾部覆盖、关键实体、重复率、每段时间合理性、说话人归属和多次运行稳定性。

## 八、最终判断

| 判断 | 置信度 |
| --- | --- |
| 端口本身不是原因，8885 代理到同一个 6006 模型服务 | 已由配置证实 |
| 两份结果使用了不同 ASR 流水线 | 已由代码与 JSON 结构证实 |
| 整段一次 ASR 是 8885 严重漏尾、重复的主要原因 | 高 |
| 全局 ForcedAligner 将错误全文拉伸，造成异常时间戳 | 已由代码和结果证实 |
| 8 kHz A-law 与 16 kHz 分段重采样差异是辅助因素 | 中，需要实机消融测试 |
| 6006 的每个字都比 8885 正确 | 尚不能断言，缺人工逐字稿 |

一句话结论：**8885 目前只是把“整段 ASR + 对齐 + 说话人贴标”包装成平台合同，并没有复用 6006 已验证较好的“说话人切段后逐段 ASR”；对这条 63 秒 8 kHz 方言电话录音，流程差异直接造成了近半文本缺失、重复和错误时间轴。**
