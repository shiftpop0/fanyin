# R9：8885 复用 6006 原生转译能力实施与验收

实施日期：2026-08-30
版本定位：R9 候选版本，已完成本地代码、合同测试和迁移材料，待 Ubuntu 生产模型验收
生产基线：R8；R8 的服务端双声道合并属于错误改动，R9 明确撤销

## 一、结论

R9 已把 `8885/v1/audiototext?diarize=1` 的文字识别来源改为与
`6006/asr?diarization=true` 完全相同的共享 Python 核心：

```text
TargetDiarization
  → 按说话人时间裁剪短音频
  → Qwen3-ASR 批量识别各片段
  → 按时间顺序组装 speaker_segments 和 overall_text
```

两个端口不再分别实现两套 `diarize=1` 识别算法。6006 直接把共享结果包装成原生
响应；8885 使用同一份 `overall_text` 和 `speaker_segments`，再执行一次本地
ForcedAligner，并转换成平台要求的 `lid/begin/end` 字幕行。

R9 同时修正 R8 的声道职责：

- 服务端不主动把文件头有效的 WAV 合并为单声道；
- Windows 浏览器采集的多声道 PCM WAV，由油猴脚本 `0.5.1` 在本机合并后上传；
- 非 WAV 输入仍可为了解码兼容由离线 ffmpeg 转成 16 kHz 单声道 WAV；
- 不修改模型、Docker 镜像、CUDA/vLLM 参数、端口、Nginx 路由或 FIFO 并发数。

## 二、为什么两个端口原来会执行不同流程

生产拓扑是：

```text
6006 /asr?diarization=true ───────────────┐
                                          ├─ 同一个 FastAPI / UnifiedService / GPU 模型
8885 /v1/audiototext → Nginx → 6006 ─────┘
```

8885 的 Nginx `proxy_pass` 保留原请求 URI。它只把网络连接转发到 6006，并不会把
`/v1/audiototext` 改写为 `/asr`。FastAPI 根据“HTTP 方法 + URL 路径”选择路由：

```text
POST /asr             → 原生 api_server.asr_api()
POST /v1/audiototext  → 平台 v1_router.audio_to_text()
```

因此，两个请求过去虽然进入同一进程、使用同一模型对象，却调用不同的 Python
业务方法。R9 的修复位置不是 Nginx，而是把两条路由的核心识别步骤下沉为同一个
`UnifiedService.transcribe_diarized_segments()`。

## 三、R8 问题与 R9 边界

R8 曾在服务端实现双声道合并成单声道。该职责后来已经确认应放在油猴脚本，原因是
浏览器端最清楚采集声道语义，并且可以在上传前完成一次确定性处理。服务端再次合并
会造成重复预处理，也会改变原生 6006 调用方提交的有效 WAV。

R9 的部署脚本和打包脚本都会检查并拒绝以下 R8 服务端 downmix 标记：

```text
pan=mono
audio channel merge
_mono.wav
merged ... channels to mono
```

这里的“不做声道合并”专指：服务端不主动改写已经是合法 WAV 的声道。非 WAV
上传走 ffmpeg 解码仍属于原有兼容路径，不代表重新引入 R8 逻辑。

## 四、R9 目标流程

### 4.1 `diarize=1`

```text
6006 /asr?diarization=true
  → UnifiedService.diarization_then_asr()
  → UnifiedService.transcribe_diarized_segments(..., fallback=true)
  → 删除仅供内部适配使用的 detected_languages
  → 保持 6006 原生 JSON

8885 /v1/audiototext?...&diarize=1
  → transcribe_platform_audio()
  → UnifiedService.transcribe_diarized_segments(
        ..., fallback=v1_diarization_fallback
    )
  → 使用相同 overall_text + speaker_segments
  → 对完整音频和完整识别文本执行一次 ForcedAligner
  → 按说话人硬边界、标点和 max_chars 生成字幕行
  → 保持 8885 v1 JSON
```

生产当前 `v1_diarization_fallback=false`，因此 8885 的说话人分离失败会明确报错；
6006 继续保留原来的整段 ASR 降级行为。二者识别成功时共用完全相同的分段 ASR
实现，失败策略则维持各自既有合同。

### 4.2 `diarize=0`

8885 继续使用整段 `asr_raw()`，再执行 ForcedAligner。它与 6006 非说话人模式保持
相同的整段识别语义。本次 R9 不额外引入 VAD 或新的长音频切分策略，以免把第二个
算法变化混入已经有明确证据的 `diarize=1` 修复。

### 4.3 两种对外响应保持不变

6006 仍返回原生结构，例如：

```json
{
  "input_file": "0051409.wav",
  "speaker_count": 2,
  "diarization_status": "ok",
  "overall_text": "完整识别文字",
  "speaker_segments": [],
  "timing_debug": {},
  "segment_workers_effective": 32,
  "request_id": "..."
}
```

8885 仍返回平台结构：

```json
{
  "code": 200,
  "language": "zh",
  "data": [
    {"lid": "1", "text": "识别文字。", "begin": 380, "end": 3210}
  ],
  "file_name": "0051409.wav",
  "message": "",
  "uuid": "..."
}
```

共享核心新增的 `detected_languages` 只在进程内部供 8885 选择响应语言使用，6006
包装器会在返回前移除该字段，避免改变原生响应合同。

## 五、代码改动

| 文件 | R9 改动 |

| `tailect/core/v1_contract.py` | 说话人变化成为硬分行边界；校验时间戳与全文覆盖；避免静默漏尾 |

| `tailect/tests/test_v1_platform.py` | 锁定共享调用顺序、无说话人模式、严格失败、说话人边界和 E016 |
| `wxz/migration/*r9*` | R9 打包、备份应用、同音频验收和恢复脚本 |

`build_caption_rows()` 现在会拒绝下列伪成功结果，并统一返回 `E016`：

- ForcedAligner 没有文本时间戳；
- 时间戳不是数字、为负、区间为空或开始时间逆序；
- 时间戳覆盖不了完整识别文本；
- 最终字幕行没有保存完整识别文本。

第一版仍使用一次全局 ForcedAligner，以维持原 v1 成本和合同。如果生产验收证明分段
ASR 文字已经一致但全局对齐仍明显漂移，再单独评估“逐说话人片段局部对齐并加回
全局偏移”，不在 R9 未实测前扩大改动。

### 7.0 已补充生产日志的验证结论

用户补充的生产日志位于本机外部只读目录：


该日志记录的是 R8/旧 v1 链路，不是 R9 运行结果，但它已经直接证实本次根因：

```text
12:37:45  8885 先记录 [ASR] audio_duration=63.3s
```

因此，R8 的 8885 确实是“整段 ASR → diarization 只贴 `lid`”，6006 则是


```text
[V1-ASR] pipeline=diarized_segment_asr
```

所以当前证据只能下列结论：

- 根因诊断已被生产 R8 日志完全证实；
- R9 的共享分段 ASR 改造直接覆盖该根因；
- 该批日志不能证明 R9 已经生产通过，反而说明采集时仍在运行旧链路；

## 八、R9 验收判断

### 必须满足

1. 6006 原生字段和数据类型未改变。
2. 8885 v1 字段、业务码、UUID、整数毫秒时间戳未改变。
3. 同一次生产模型运行中，8885 拼接文字严格等于 6006 `overall_text`。
4. `0051409.wav` 不再在“你叫什么名字”处漏掉后续姓名、案件确认和结束语。
5. 双人音频至少得到 `lid="1"`、`lid="2"`，且说话人变化不会被聚合到同一字幕行。
6. 对齐无法覆盖全文时明确返回 `E016`，不能把尾部文字静默丢弃。
7. 6006/8885 仍共用一个模型进程，8885 FIFO 仍为并发 1。
8. 服务日志不出现 R8 的服务端声道合并信息。

### 仍需人工判断

- 方言地点、窄带易混词和姓名实体是否正确；
- 说话人边界、重叠语音和时间戳是否符合听感；
- R9 延迟和显存峰值是否满足生产要求；
- 多次调用结果是否稳定。

“8885 与 6006 文字一致”证明共享流程成功，不等于识别文字已经逐字正确。最终质量
应以人工逐字稿和 CER 为准。
