## 1. 问题摘要

在同一张 RTX 5090、同一服务和完全相同的 2～5 分钟真实普通话 WAV 输入上，观察到如下稳定差异：

- 关闭说话人分离时，测试程序调用原生接口 `POST /asr_raw`。接口返回可解析 JSON，且存在字符串字段 `text`，因此当前测试框架将请求判定为成功；但四份音频分别只返回 8～22 个字符，内容仅为标题或音频中的一句话，未覆盖完整音频。
- 开启说话人分离时，测试程序调用原生接口 `POST /asr?diarization=true`。四份音频均返回 `diarization_status=ok`，分段时间轴覆盖到音频末尾，输出为 390～937 个字符。
- 因此，当前问题不是“接口报错”，而是 `/asr_raw` 在 HTTP/结构层面成功、业务输出却严重不完整的**静默截断/假成功**。

严重级别建议：**高**。如果生产系统只检查 HTTP 200 和 `text` 是否为字符串，这类请求会被当作成功入库，无法依靠普通失败重试发现。

## 2. 与 E016 问题的边界

本问题不要与 8885 平台接口的 E016 混为一谈：

- 本问题来自原生接口对照：`/asr_raw` 与 `/asr?diarization=true`。
- `/asr_raw` 响应只有 `text`、`language`，没有执行全局 ForcedAligner 的证据；当前现象是 ASR 文本本身明显过短。
- E016 是 8885 `/v1/audiototext?diarize=0` 路径中，ForcedAligner 字符时间戳数量与 ASR 字符数量不一致导致的平台业务错误。
- 两个问题可能共享部分上游音频处理代码，但表现、接口路径和直接故障点不同，需分别建回归用例。

## 9. 优先排查方向

建议技术人员按以下顺序定位。

### 9.1 `/asr_raw` 是否完整读取音频

在进入 ASR 前记录并比对：

- 上传文件字节数；
- 解码后的采样率、声道、总采样点数；
- 解码音频时长；
- 实际送入模型的音频时长；
- 是否存在固定时长裁剪、最大采样点限制或只读取首个数据块的逻辑。

验收时，2/3/4/5 分钟输入的“实际送入模型时长”应分别接近 120/180/240/300 秒。

### 9.2 长音频切块后的结果聚合

重点检查 `/asr_raw` 内部是否进行切块或批处理，以及：

- 是否只返回了首块、末块或某一批次的文本；
- 循环中是否用赋值覆盖了累计结果，而不是追加并按顺序拼接；
- vLLM 批量返回结果与输入切块的索引是否错位；
- 某个切块空输出时，是否错误终止整个聚合过程；
- 异步任务是否在所有 future 完成前就构造响应。

`real_004m_01.wav` 的 d0 文本来自音频中间位置，说明问题不一定只是“只处理第一块”，还应检查批次索引和最终结果覆盖。

### 9.3 解码提前停止条件

记录每个音频块的：

- 输入 token/音频特征长度；
- 输出 token 数；
- `finish_reason` 或停止原因；
- `max_tokens`/最大生成长度；
- EOS、标点或语言控制 token；
- 是否因为模型输出标题和句号而把整份音频任务判为完成。

### 9.4 `language=Tiantai` 异常

四份普通话音频均返回 `Tiantai`。需要确认：

- 该字段是语言、方言还是模型内部标签；
- 是否启用了错误的自动语言检测结果；
- 该标签是否进入 ASR prompt/control token；
- 强制普通话/中文语言参数后，截断是否消失。

### 9.5 比较 `/asr_raw` 与 `/asr?diarization=true` 的代码路径

`diarize=1` 路径会先得到说话人片段，再逐片段 ASR 并聚合，四份材料均覆盖完整时长。这说明：

- 音频文件本身可被服务正确解码；
- ASR 模型能够识别这些内容；
- 问题更可能位于 `/asr_raw` 的整段输入、切块、批次映射或输出聚合，而不是材料损坏或模型完全不能识别。

建议用同一个 WAV，在两条路径中记录统一的中间结构：解码时长、切块边界、块数量、块级文本、块级停止原因和最终聚合文本，逐阶段比对首次出现差异的位置。

## 10. 监控与成功判定需要同步修正

即使修复服务，也建议修正调用方/测试框架，避免再次把静默截断算作成功。

最低要求：

- 不应仅以 HTTP 200 且 `text` 为字符串作为完整成功标准；
- 原生接口响应建议增加 `input_duration_seconds`、`processed_duration_seconds`、`chunk_count`、`completed_chunk_count`、`finish_status` 和 `request_id`；
- 当 `processed_duration_seconds` 明显小于输入时长时，返回明确非成功状态，不能静默返回局部文本；
- 对无时间戳的 `/asr_raw`，字符数密度只能作为告警信号，不能作为唯一失败标准，因为音频可能包含长静音；
- 对带时间戳的结果，应校验末段时间是否接近音频末尾，并允许合理的尾部静音容差。

## 11. 修复验收标准

修复后至少满足以下条件：

1. 对本文四份原始 WAV 重跑 `/asr_raw`，服务明确记录完整处理 120/180/240/300 秒输入。
2. `/asr_raw` 不再只返回 8～22 个字符，结果在内容覆盖上与 `diarize=1` 基本一致；由于切段和解码策略不同，不要求逐字完全相同。
3. 不允许以 HTTP 200 静默返回局部识别结果；若无法处理完整音频，必须返回可识别的失败/部分完成状态和已处理时长。
4. 普通话材料的 `language=Tiantai` 异常得到解释或修复。
5. 增加 2、3、4、5 分钟 8kHz/16-bit/mono 单人普通话回归用例，并至少补充 1、10、20、30 分钟边界样本。
6. 回归同时覆盖 `/asr_raw`、`/asr?diarization=true` 和 8885 `/v1/audiototext`，并分别报告 HTTP 状态、业务状态、输出完整性和时间戳覆盖率。

## 12. 当前能够确认与尚不能确认的事项

已确认：

- 四份材料格式合法且可被 `diarize=1` 路径完整处理；
- `/asr_raw` 输出长度严重异常；
- 异常可跨 2～5 分钟材料复现；
- `diarize=1` 的分段时间覆盖至每份音频末尾；
- 当前 `diarize=0` 成功判定存在漏检静默截断的问题。

尚不能仅凭现有结果确认：

- `/asr_raw` 内部到底是音频读取、固定长度裁剪、vLLM 解码停止、批次索引还是聚合覆盖错误；
- 两种路径识别文本的准确率差异，因为没有片段级时间对齐人工字幕；
- `language=Tiantai` 是根因、伴随现象还是字段命名问题。

上述三项需要结合服务端块级日志和代码路径进一步定位。
